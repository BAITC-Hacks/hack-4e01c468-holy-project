# Своя турбина: координаты, CSV и обучение

Дата: 2026-09-23. Статус: проект для проверки пользователем; реализация не начата.

## Цель и границы

Подтверждённый сценарий: пользователь вводит название и координаты своей турбины, загружает CSV наблюдений, запускает обучение, выбирает эту турбину и получает прогноз на 24/48 часов. Две существующие турбины остаются доступными по умолчанию вместе с существующими данными и моделями.

Предположения первой версии: локальное однопользовательское приложение; одна пользовательская запись соответствует одной турбине и одной точке погоды; мощность нормализована в [0, 1]; измерения имеют шаг 10 минут. Новая турбина обучается только на собственных наблюдениях и исторических прогнозах погоды по её координатам. Добавление произвольных файлов, обучение на любых данных и приемлемая точность для любой площадки сейчас не поддерживаются и не обещаются.

Вне первой версии: аккаунты, доступ из интернета, парк пользовательских турбин в одном запуске, перенос моделей между площадками, автоматическое определение единиц/часового пояса, загрузка моделей пользователем, SCADA в реальном времени, оптимизация гиперпараметров и массовое переобучение. Новый обязательный объект «ветропарк» пользователю не нужен.

## Варианты и рекомендуемый подход

1. **Реестр + изолированный контекст в существующем монолите — рекомендуется.** Существующая пара образует контекст `default`, каждая пользовательская турбина — отдельный контекст с одной записью. Общие алгоритмы получают явные ID/координаты/датасет. Это сохраняет существующий сценарий и позволяет проверить отсутствие смешивания данных.
2. **Добавлять все турбины в одну общую модель.** Потребуется переобучать общий набор, менять полную прогнозную сетку и координировать разные источники/даты. Ошибка пользовательского CSV затронет существующий сценарий. Для первого расширения избыточно.
3. **Отдельный сервис для пользовательских турбин.** Даёт инфраструктурную изоляцию, но дублирует pipeline и сопровождение. Текущему локальному продукту достаточно модульного монолита.

## Пользовательский поток

1. В выборе объекта первоначально выбран «Две исходные турбины»; рядом действие «Добавить турбину».
2. Форма: название, широта, долгота, CSV. Рядом шаблон и пояснение единиц/времени. После проверки показываются период, пригодные часы, пропуски и ошибки с номерами строк.
3. Валидный файл сохраняется как версия датасета. Короткий корректный файл можно сохранить: запись будет «Недостаточно данных для обучения», с числом недостающих пригодных строк/периодов.
4. Карточка предлагает «Обучить». Перед запуском видны выбранные даты, число исторических погодных запросов и лимит загрузки; выбранный план фиксируется в задаче. Прогресс: проверка → погода N/M → признаки → обучение → калибровка → сохранение. Не показывать выдуманный процент для CatBoost.
5. После успешного сохранения модель активируется атомарно. В выборе появляется доступный прогноз пользовательской турбины. Видны версия данных, дата обучения, последняя доступная телеметрия и предупреждение об устаревании.
6. Обновление CSV создаёт новую версию. Старая модель остаётся исторически доступной; новая версия не использует её незаметно. Первая версия требует обучения под новый выбранный датасет.

Название выводится как текст, включая в SVG/таблицах; не вставляется в HTML без экранирования. При переключении объекта старые графики и результаты не показываются под новым названием. Latest-run запрашивается с контекстом. Отсутствующая после перезапуска запись сбрасывает выбор на default с понятным сообщением. RU/KK и тема сохраняются.

## Контракты и слои

Ниже предложенные сущности, пути и API; их пока нет в продукте. Расширение следует `skills/architecture.md`, без общего переноса всех модулей в `src/`.

**Turbine:** серверный неизменяемый `turbine_id`, `scope_id`, название (1–100 символов после trim), конечные latitude [-90, 90] и longitude [-180, 180], `builtin`, версия координат. Исходные ID `turbine_1`, `turbine_2` и координаты из `weather.py` сохраняются. Пользовательские ID генерирует сервер; имя не является ключом или каталогом. Редактирование координат после импорта в первой версии не поддерживается: новая площадка требует новой записи.

**DatasetVersion:** `dataset_id`, `scope_id`, raw_sha256, prepared_sha256, версия схемы/агрегации, импортный формат, семантика времени и единиц, период и статистика качества, время импорта. Загрузка закреплена за одной турбиной сервером: CSV не выбирает чужой ID. Источник и prepared сохраняются неизменяемыми.

**ForecastContext:** зафиксированные `scope_id`, список Turbine, версия координат, `dataset_id`, fingerprint данных, weather_source, feature_schema, временная политика. Разрешается через реестр один раз при допуске задачи. Нельзя переключать глобальные константы или менять settings/_history общей Application между запросами. Bootstrap собирает отдельный runtime для контекста; legacy-обёртка без явно указанного контекста выбирает default.

**ModelVersion:** контекст, допустимые turbine_ids, dataset fingerprint, provider/model/policy погоды и fingerprints использованных снимков, feature_schema, версия кода и зависимостей, параметры/seed, даты и row counts train/calibration, calibration status, хеши файлов. Совпадение только turbine_id или названия файла недостаточно. Для пользовательской модели допустим только её singleton-набор; для legacy-модели — исходная пара.

**TrainingJob:** job_id, kind, scope_id, dataset_id, immutable plan, state (`queued/running/completed/failed/interrupted`), stage, выполненные/общие origins, загруженные байты, timestamps, безопасная ошибка, model_id при успехе. После аварийного рестарта running становится interrupted; повторный запуск переиспользует только законченные и проверенные снимки. Автоматическое возобновление fit не требуется.

Размещение новых частей:

- `domain/`: Turbine, DatasetVersion/ссылки, ForecastContext и ошибки валидации.
- `application/turbines/`, `application/training/`: регистрация, импорт/проверка, планирование и обучение. Малые repository-порты добавить рядом с существующим `application/ports.py`, не превращая его в пакет в этой задаче.
- `infrastructure/datasets/`, `infrastructure/persistence/`: CSV adapter, файловый реестр, датасеты, модельные указатели и журнал задач.
- `presentation/api/`: тонкие routes/schemas и локальная защита запросов. `bootstrap.py` связывает зависимости.
- `frontend/src/features/turbines/`: форма, отчёт импорта, состояние обучения, selector. Признаки и ML остаются в текущих модулях с явным контекстом; дальнейшее перемещение независимо.

Для локального приложения достаточно JSON-реестра с schema_version, короткой блокировкой изменения и записью temporary + atomic replace. Поддерживается один процесс API; несколько серверных workers не допускаются, пока допуск задач и блокировки не станут межпроцессными.

## CSV: строгая и проверяемая первая версия

Два явно названных формата, без эвристического сопоставления колонок:

- Канонический UTF-8/UTF-8 BOM CSV, запятая, десятичная точка: `timestamp,power,wind_speed,temperature`. ISO-8601 timestamp обязательно с Z или числовым offset; шаг сетки 10 минут. `power` нормализована, wind_speed в m/s, temperature в °C.
- Совместимость с текущим CSV: четыре заголовка из `data.py:SOURCE_COLUMNS`, timestamp `YYYY-MM-DD HH:mm:ss`, явно показанное пользователю толкование UTC+05. Этот режим сохраняет поведение исходного набора.

Оба формата переводятся в общий RAW_COLUMNS; затем используется часовая агрегация. Разное представление времён сводится к UTC до поиска дублей. Полностью совпадающие дубли схлопываются и учитываются; конфликтующие измерения одного момента блокируют импорт. Несоответствие схемы/кодировки, неверные timestamps, infinity, нечисловые значения, power вне [0,1], отрицательная скорость и timestamps вне 10-минутной сетки блокируют пользовательский импорт с кратким отчётом. Пропущенные строки допустимы и отражаются пропусками; некорректные значения нельзя молча превращать в ноль. Температура проверяется на конечность; неподтверждённые климатические пороги не вводятся.

Начальные настраиваемые пределы: 25 MiB, 250 000 строк, 64 колонки, 16 KiB на запись, период не больше 366 суток; потоковое чтение с реальным счётчиком байтов, не только Content-Length. До построения полной почасовой сетки проверяется длительность: две строки с разницей в столетие не должны выделять гигантский DataFrame. Пустой файл, архив, XLSX и HTTP URL вместо файла не принимаются. Количество ошибочных примеров в ответе ограничено (20); полный сырой файл в ошибки/логи не попадает.

Внешний доступ отсутствует, но новые POST обязаны получить ту же host/origin защиту, что forecast-jobs. В текущем middleware проверка origin/типа/размера действует только на этот один POST: её нельзя просто считать уже общей. Для JSON оставить небольшой лимит, для CSV — отдельный потоковый лимит. Пути/имена файлов/URL от клиента не использовать; сервер генерирует каталог и проверяет containment и symlink. Импорт идёт во временный файл и публикуется только после проверки. Не принимать pickle/CBM от пользователя.

## Обучение и честность по времени

Для пользовательских данных нет календарных значений 2025/2026 в бизнес-правилах. План строится из пригодного интервала UTC. Выбираются максимум 17 суточных origins: 14 для обучения, 3 более поздних для калибровки, горизонт 48 часов. Последняя калибровочная цель должна целиком попадать в наблюдения. До первого train origin резервируется 168 часов для имеющихся lag-признаков; пропуски остаются явными missing-признаками. Train-цели обрезаются первым calibration origin, включая пересекающийся хвост 48-часового горизонта.

Начальный технический допуск: все 17 origins с доступным историческим погодным прогнозом, не менее 300 пригодных train pairs и 30 calibration pairs для своей турбины; отдельно сообщать число уникальных target-hours, число origins и coverage. Перекрывающиеся 48-часовые горизонты дают повторные цели, поэтому число pairs нельзя выдавать за число независимых наблюдений. Это консервативная продуктовая политика запуска, а не доказательство достаточной статистики или точности; её версионировать. Ровный достаточный CSV обычно потребует порядка 3–4 недель, точный допуск вычисляется по фактическим датам и пропускам.

Наблюдения для признаков допускаются только при available_at ≤ origin; часовой target доступен после окончания часа. Как сейчас, available_at = hour_start + 1h — предположение о доступности телеметрии, а не доказательство из времени загрузки файла. Отразить `observation_availability_policy=hour_end_assumed` в manifest. Если требуется оценка при реальных задержках SCADA, нужен отдельный контракт available_at и изменение hourly validator; первая версия этого не заявляет.

Историческая погода должна доказывать available_at ≤ каждый origin; initialized_at недостаточно. NOAA adapter использует архивный LastModified как верхнюю границу публикации. Координаты запроса и фактическая ближайшая точка сетки сохраняются в provenance. Нельзя подменить отсутствующий архив современной погодой, реанализом или синтетикой и назвать результат проверенным обучением.

Train и calibration хронологически разделены; max(train target_end) ≤ min(calibration origin). В inference train/calibration cutoff ≤ request origin. Определение локальных часов для новых турбин: в первой версии UTC-признаки и UTC seasonal baseline; исходная пара сохраняет UTC+05. Это явно версионируется в feature schema и модели. Часовой пояс отображения интерфейса не меняет ML-признаки; отдельный географический timezone lookup не требуется.

Без годных данных — `insufficient_data` с конкретными счётчиками, без модели и прогнозных нулей. Без архива — `historical_weather_unavailable`, датасет остаётся сохранённым. Наличие CSV само по себе не даёт кнопку успешного прогноза. До первого успешного обучения пользовательский прогноз возвращает `model_not_ready`. После обучения допустим только fallback baseline, построенный на тех же данных/контексте, с явным degraded; исходные модели никогда не подставляются.

Калибровочные метрики маркируются как calibration, не test/backtest. Независимый rolling backtest — отдельная будущая работа; его отсутствие отображается как «Нет оценки». Отсутствие истины после конца CSV исключает фактические метрики будущего прогноза. При устаревании последних наблюдений более чем на 24 часа сохраняется нынешнее предупреждение/degraded. Квантильные интервалы не называются доказанно калиброванными: текущая CatBoost-модель возвращает собственные квантильные оценки, а residual calibration не используется для их построения.

## Изоляция хранения и совместимость

Предлагаемые пространства хранения:

```text
data/registry/turbines.json
data/raw/<scope_id>/<dataset_id>/source.csv
data/processed/<scope_id>/<dataset_id>/hourly.csv + manifest.json
artifacts/models/<scope_id>/<dataset_id>/<weather_identity>/<model_id>/...
artifacts/models/<scope_id>/<dataset_id>/<weather_identity>/active.json
artifacts/jobs/<job_id>.json
.cache/wind/scopes/<scope_id>/...
artifacts/runs/<existing-run-id>/...  # общая адресация, явный scope в manifest
```

У prepared cache ключ включает raw hash + parser/aggregation/time-policy version. У приложения и provider-кэша: scope + turbine IDs/координаты/версия + provider/model/policy + origin/horizon + режим; погодный fingerprint содержит стабильное доказательство источника. У модели/reuse дополнительно dataset, feature schema, train/calibration cutoffs, параметры, seed, зависимости и code identity. Baseline selection, folds и metrics также отдельны: сегодняшний общий `backtest/metrics.json` нельзя читать для новой площадки.

Active pointer обновляется только после полной проверки bundle; ошибка/остановка обучения не затрагивает предыдущий bundle. Каталоги моделей не передаются из HTTP. Изменение координат, источника погоды, CSV, схемы или временной политики делает старую модель несовместимой. Не допускается повторный расчёт из кэша другой турбины даже при одинаковом origin и одинаковых числах погоды.

Legacy-данные/модели регистрируются как default, остаются на прежних путях и читаются совместимым adapter. Старые manifests без scope интерпретируются только как default; для custom не допускаются. Новые manifests имеют новую версию и scope/dataset/coordinates identity. Автоматического переноса/перезаписи текущих артефактов и работающего NOAA bootstrap нет. Вызовы CLI без выбора объекта сохраняют исходную пару; аргумент выбора объекта добавляется после общего application use case.

## Эволюция HTTP API

Все перечисленные изменения проектируются; сейчас существуют только forecast-jobs и чтение runs/health. Ответ импорта и записи GET turbines включают рассчитанный без сети training_plan/его plan_fingerprint, пригодность и бюджет; поэтому пользователь видит будущий объём до запуска. POST training-jobs принимает также этот plan_fingerprint и отклоняет устаревший план, а все конкретные даты и лимиты повторно проверяет сервер.

| Метод/маршрут | Назначение |
|---|---|
| GET `/api/turbines` | Две встроенные и пользовательские записи, scope_id, dataset/model status; без локальных путей |
| POST `/api/turbines` | JSON name/latitude/longitude → 201, серверные turbine_id/scope_id |
| POST `/api/turbines/{id}/datasets?format=canonical-v1` | Тело `text/csv` (либо явно выбранный legacy-v1) → 201 dataset + quality; при ошибке 422, версия не публикуется |
| POST `/api/training-jobs` | JSON scope_id/dataset_id/plan_fingerprint → 202 job; сервер проверяет и фиксирует ограниченный план |
| GET `/api/training-jobs/{job_id}` | Статус, стадия, прогресс, безопасная ошибка/модель |
| POST `/api/forecast-jobs` | Существующие origin/horizon/refresh + необязательные scope_id/dataset_id; отсутствие scope выбирает default |
| GET `/api/runs/latest?scope_id=...` | Последний run выбранного контекста; без scope_id выбирается только default, включая случаи, когда самый новый run относится к пользовательской турбине |

Если dataset_id опущен для custom forecast, сервер разрешает текущую выбранную версию при допуске и закрепляет её в задаче; более поздний импорт не меняет выполняющийся запрос. Training всегда указывает dataset_id явно. Существующие GET `/api/forecast-jobs/{id}`, `/api/runs/{run_id}` и download CSV сохраняют адреса. HTTP 409 — тяжёлая задача занята или состояние не позволяет операцию; 404 — неизвестный ID; 413/415 — лимит/тип файла. Дублирование нажатия не запускает второй fit; повторный идентичный план возвращает текущую задачу либо сохранённый совместимый результат.

В ответе нового прогноза scope/dataset/model указаны в manifest; frontend проверяет соответствие текущему выбору до отрисовки. Latest без scope_id никогда не выполняет глобальный поиск среди всех контекстов: если default-run отсутствует, возвращается прежнее состояние «Нет запуска», даже при наличии пользовательских runs. Старый manifest без scope считается только default. Сервер не принимает произвольные директории, provider URL, параметры CatBoost, диапазон скачивания на годы или готовый «проверенный provenance» от клиента.

## CPU, сеть и фоновые задачи

Базовый допуск — одна тяжёлая задача на весь локальный сервер, общая для forecast/train; без неограниченной очереди. Во время обучения чтение статуса и готовых результатов работает, новая тяжёлая задача получает 409. Это сознательный компромисс первой версии; UI заранее сообщает занятость. Короткие записи реестра имеют отдельную блокировку.

CatBoost CPU: сохранить фиксированные 250 iterations/depth 6/seed 42, максимум min(4, доступные CPU) threads; три квантильные модели последовательно. Для исполнения лимита времени обучение запускается отдельным дочерним процессом под ограниченным runner, а не через попытку отменить уже работающий Python-thread. Родитель управляет статусом/активацией, ребёнок пишет staging bundle. Celery/Redis не нужны. Без subprocess рабочий ThreadPoolExecutor можно сохранить только на этапе прототипа: он не обеспечивает принудительное прекращение fit.

Цена NOAA значительна: текущий adapter на один origin/48h запрашивает 48 индексов и 48 × 7 = 336 диапазонов GRIB; для 17 origins — 5712 диапазонов плюс 816 индексов, listing/метаданные и retries. Один диапазон содержит поле глобальной сетки, а не несколько байт точки. Близость координат сама по себе не делает новую загрузку дешёвой.

Предлагаемые стартовые ограничения: максимум 17 origins/задачу; один активный сетевой запрос; существующие не более 3 попыток и таймауты (5,30) секунд на HTTP; 60 минут на всю задачу, включая 10 минут на fit; бюджет сети 8 GiB и staging/cache 2 GiB на задачу. Счётчики учитывают retries и реально прочитанные байты; при превышении — `resource_budget_exceeded`, без активации модели. Это лимиты защиты, не обещание, что 17 origins в них поместятся: необходим замер реального холодного запуска, после него параметры допуска корректируются явно.

Проверенный point-extract cache повторно используется по полному ключу; успешные origins сохраняются при сбое. Полный глобальный GRIB cache/совместное выделение многих площадок можно сделать позже, если измерение покажет сетевой узкий участок. Нельзя запускать экспериментальный bulk download рядом с текущим bootstrap; дизайн не требует такого эксперимента сейчас.

## Минимальные этапы и критерии приёмки

1. **Контекст и регрессия.** Параметризовать IDs/координаты во всей цепочке (включая quality gate, persistence и demo fixtures), сохранить default. Проверить singleton и исходную пару на малых offline fixtures; разные площадки/датасеты/провайдеры не переиспользуют модели, snapshot и runs друг друга. Ориентир: 1–2 рабочих дня.
2. **Реестр и импорт.** Сохранение записи, безопасный upload, версии/качество, границы файлов и состояний. Проверить некорректные числа/таймзоны/дубли, огромный диапазон времени, прерванный upload, restart. Ориентир: 1 день.
3. **Обучение и выбор модели.** План по датасету, ограниченный runner, сохраняемые статусы, временные проверки и атомарная активация; отрицательные тесты утечки и неправильного context. Модели для custom не обучаются скрыто из `_ensure_model` при запросе прогноза. Ориентир: 1–2 дня.
4. **UI и полная проверка.** Добавление → качество → обучение → выбор → 24/48h → CSV → рестарт, обе локали, мобильная версия, error/degraded states. Default по-прежнему даёт 48/96 строк, custom — 24/48. Ориентир: 1 день.

Итого инженерная оценка: примерно 4–6 рабочих дней с интеграционными проверками; около 20–30 существующих файлов затрагиваются из-за фиксированного набора турбин, плюс небольшие новые модули. Это оценка сложности, не обещание срока. Один интерфейсный проход не завершает функцию. Сетевой bootstrap/архивные ограничения могут увеличить календарное время независимо от разработки.

Обязательные проверки: прежний Python/frontend suite; контракты API с default; поведение неизвестного ID; selection/latest-run; несовместимый model manifest; bounds/containment; перезапуск и прерванный fit; датасет другой турбины; координаты при одинаковом ID; train/calibration/inference leakage; архив без доказательства времени; недостаточные данные; budget exceeded; один реальный небольшой погодный запрос новой точки после offline-проверок и при свободном общем ресурсе. Полный реальный train проверяется отдельно и не подменяется mock-успехом.

## Блокеры и решения перед реализацией

Технические обязательные работы: сквозное снятие ограничения двух ID, безопасный новый upload boundary, независимые application instances/идентичности и выделенный training workflow. Сейчас их нет; это не готовая возможность, спрятанная в UI.

Внешний блокер конкретного пользователя возможен, если нет достаточно качественной истории либо архив не доказывает доступность погоды на её даты. В таком случае регистрируем/проверяем данные и честно сообщаем, почему обучение недоступно. Не обещаем восстановить отсутствующий архив.

Для review требуется подтвердить предложенный предел первой версии: 10-минутная нормализованная телеметрия, изолированная пользовательская турбина и отдельное обучение при сохранении исходной пары. Следующий артефакт после review — конкретный implementation plan по этапам; этот документ не запускает реализацию и не меняет текущие NOAA/UI задачи. Ссылки на владельцев проверок отражают момент чтения: параллельный architecture batch переносит quality gate/weather policy в `application/forecasting/`; при реализации изменять актуальный владеющий модуль, сохранив описанные инварианты.
